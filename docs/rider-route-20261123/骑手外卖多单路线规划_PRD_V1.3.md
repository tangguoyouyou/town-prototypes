# 骑手外卖多单路线规划 · 需求文档

版本：V1.3 · 2026-11-27 · 本地评审版

## 1. 功能说明

本次增加骑手多单路线规划功能。针对骑手在手的已出餐待取货、已取货待送达外卖订单进行路线规划（包括闪购订单）；本轮最多参与公共配置max_tasks单，取送顺序遵守carry_limit携带上限。不调整派单规则、不处理跑腿订单、万能帮订单、闪购退款退货订单、代购门店订单、商家自配送、自提订单、顺丰订单、第三方配送订单。

骑手接单列表保留原排序和订单操作，新增独立【路线】规划页面，展示本轮选入订单的建议取送顺序，超出本轮单数上限的订单明确列入暂未参与。订单新增、归属或状态变化后整体重新规划；用户端的前方单数随有效路线更新，预计送达沿用订单记录。

**本次调整范围**

| 端或页面 | 调整内容 |
| --- | --- |
| 总后台 | 【新增】运营管理→平台系统设置的路线总开关；小镇管理→配置信息的小镇开关；订单管理→订单推送查询下方新增【骑手路线规划】，查询已生成规划记录及详情；公共配置新增路线参数，时间估算读取对应配置 |
| 骑手APP | 【新增】独立路线入口／页面、个人规划开关和软线容差（为规划路线使用的超时，跟订单的实际超时没关系）；【修改】订单变化后整体重排及平台或小镇关闭权限后的展示 |
| 用户端 | 【新增】本人前方单数随有效路线更新。预计送达沿用订单记录 |



## 2. 总后台

### 2.1 骑手路线规划总开关

**功能规则**

1、【新增】总后台“运营管理→平台系统设置”增加“骑手路线规划开启”，选项为【开】【关】，默认【开】，使用页面已有【保存】操作。以保存成功的值控制权限；
2、平台开关是全局权限。开启后，各小镇仍由自身开关控制，见[2.5 小镇骑手路线规划开关](#25-小镇骑手路线规划开关)。关闭后，骑手端按[3.1.6 平台及小镇权限、个人开关与容差](#316-平台及小镇权限个人开关与容差)在进入页面、保存、刷新或重规划时读取最新权限。

**UI交互流程**

1. 总后台进入【运营管理→平台系统设置】。
2. 在已有配置下方查看“骑手路线规划开启”，选择【开】或【关】，默认【开】。字段名称左侧增加问号，鼠标悬停时显示“平台与所属小镇均开启后显示规划设置，骑手个人也开启后显示外卖列表路线入口。”，移出后隐藏。
3. 点击页面【保存】，成功后按所选值控制骑手端权限；
4. 按[3.1.6 平台及小镇权限、个人开关与容差](#316-平台及小镇权限个人开关与容差)验证已打开的骑手设置、路线页以及外卖列表。


该开关与【公共配置→骑手路线规划参数】的open为同一配置值，不能维护两套独立总开关。

**菜单与页面职责**

1、【新增】总后台【订单管理】下增加【骑手路线规划】，紧接【订单推送查询】下方、位于【订单距离查询】上方。
2、页面用于查询骑手已经生成的路线规划记录，点击【规划详情】查看该次规划。不在本页面修改骑手设置、订单状态或重新计算路线。

**查询区域**

| 条件或按钮 | 展示及操作 |
| --- | --- |
| 骑手信息 | 一个输入框，提示“手机号 / 骑手姓名 / 骑手编号”，按输入的骑手信息查找规划记录；手机号需要脱敏展示，中间四位隐藏 |
| 时间筛选 | 开始日期、结束日期，按照生成的规划时间查询，结束时间大于等于开始时间，默认显示近7天的数据，结束时间为当天数据；单次查询不超过31天 |
| 查询 | 按已填写的骑手信息和时间筛选列表；结果为空时展示无符合条件记录 |
| 重置 | 清除已填写条件，恢复页面初始查询状态 |

**记录列表**

| 字段 | 展示口径 |
| --- | --- |
| 骑手编号、骑手姓名、骑手手机号、所属小镇 | 显示本次规划对应的骑手信息以及骑手所属小镇；手机号脱敏展示；所属小镇格式为“【ID】小镇名称”，例如“【104】八千小镇”；ID与名称均取该条规划记录对应的所属小镇 |
| 在手单量 | 本次规划的骑手手里的待取货和待送货的外卖订单总数 |
| 超时情况 | 统计规划预计完成时间大于“订单最晚送达时间”的订单数；如果订单已经超过了最晚送达时间，UI需要标红；问号说明：硬线超时:规划预计完成时间大于“订单最晚送达时间”的订单数，红色表示已经存在超时订单；|
| 软线超时 | 统计规划预计完成时间大于“订单最晚送达时间＋骑手软线容差”的订单数；问号说明：在硬线超时基础上叠加骑手设置的软线容差后仍超时的订单数，用于提前预警(软线=最晚送达时间+软线容差) |
| 预计总时长 | 本次可执行路线全部交付完成的预计耗时，单位分钟；不包括暂未参与订单的等待耗时；问号说明：按本次规划的路线顺序，依次完成全部取餐、送达动作等预计所需的总分钟数； |
| 距离来源 | 本次规划实际记录的距离或骑行估算来源，当前项目使用的是腾讯地图；问号说明：规划所用的距离数据来源:腾讯骑行(真实路线距离)；线距离(距离接口失败时降级为球面直线估算) |
| 计算耗时 | 生成本次规划所记录的计算耗时，单位ms；问号说明：本次规划算法的计算耗时(毫秒);含距离矩阵获取与路线求解 |
| 软线容差 | 读取该次规划实际采用的软线容差，如果骑手设置的软线容差小于等于公共配置，就展示骑手设置的，如果大于公共配置，展示公共配置的，单位分钟；问号说明：记录该次规划实际采用的软线容差。如果骑手设置的软线容差小于等于公共配置，就展示骑手设置的，如果大于公共配置，展示公共配置的，单位分钟 |
| 规划时间 | 该条规划记录生成的时间，精确到秒 |
| 操作 | 【规划详情】，打开该条记录详情 |

**两个超时口径**

- 硬线超时：本次规划预计完成送达时间＞订单真实最晚送达时间。此处是规划结果中的预计超时，不据此认定订单事后已实际超时。
- 软线超时：本次规划预计完成送达时间＞订单真实最晚送达时间＋骑手软线容差。即用户明确的“超过骑手设定软线容差的订单”。
- 两项均按独立订单计数，等于时限不算超过；同单的取餐动作不重复计数。沿用[3.1.3 预计到达、预计送达与超时计算](#313-预计到达预计送达与超时计算)的完成交付口径，不以到达收货点代替完成。
- 例如最晚12:30、允许5分钟，预计12:32完成：硬超时1单，软线超时0单；预计12:36完成：两项均为1单。个人设置不改变原订单时限。

本页读取每次已生成的记录。打开历史记录时，其时间、容差及计算结果保持该次记录值，不用骑手当前设置或最新路线替换。记录保存时长、失败规划是否入表、默认排序及具体可见角色沿用现有后台规则后核对【待确认】。

“硬超时”在历史规划中表示该次预计无法按订单时限送达，不等同于已完成订单的事后超时认定。容差内的预计超时仍计入硬超时；软线超时只统计超过最晚送达时间加容差的订单。


### 2.3 路线规划详情

**打开与关闭**

点击记录行【规划详情】打开“路线规划详情”，顶部左侧【×】关闭，返回原查询结果；保留查询条件。详情只读，不提供订单取送、改派、配置保存或重算操作。

**规划概览**

| 字段 | 内容 |
| --- | --- |
| 骑手 | 姓名及ID，例如“岳志豪（9301234）” |
| 手机号、所属小镇 | 该记录中的脱敏手机号与所属小镇；小镇与列表一致，按“【ID】小镇名称”展示，例如“【104】八千小镇” |
| 规划时间、骑手位置 | 该次规划的时间及骑手经纬度，经纬度是规划路线时候记录的骑手经纬度 |
| 软线容差 | 该次规划采用的骑手个人允许超时分钟数 |
| 在手单量 | 跟列表展示一样 |
| 软线超时、硬线超时 | 跟列表展示一样 |
| 预计总时长、距离来源、计算耗时 | 跟列表展示一样 |

**下一步与规划顺序（先取后送）**

概览下方以浅橙提示显示“下一步：动作＋订单号”，对应规划顺序第一步。没有可执行步骤时该栏目不显示。

| 规划顺序字段 | 展示说明 |
| --- | --- |
| 顺序 | 按本次规划依次展示序号 |
| 动作 | 展示规划的订单需要操作的动作，展示取餐或送达；同单需要先取后送，已取餐仅保留送达 |
| 订单号 | 对应的完整订单号，不用骑手端短号替代 |
| 门店／收货 | 如果是取餐动作，显示门店名称，如果是送达动作，显示订单的收货地址信息，不需要显示用户的信息；信息过长可以换行，需要全部显示出来 |
| 预计到达、预计完成 | 按照规划的预计到达，预计完成时间展示，包含当前动作交付或停留耗时 |
| 状态 | 按订单真实最晚送达时限展示该次规划的预计状态，如准时、预计超时；不与排序容差混用 |
| 建议 | 展示该次规划记录的建议； |

**暂未参与订单**
分为三种：①商家未出餐，②超过了公共配置的规划订单上限，③订单状态变更为不符合条件的，例如变更为转单中/退款中。如果是商家未出餐，显示“未出餐，暂未参与规划”；如记录中存在转单暂缓订单，按既有参与规则显示真实转单原因；如果是退款中，显示：退款中，暂未参与规划。如果是超过规划订单上限，提示：超过本轮规划单数上限。暂未参与订单不编入执行顺序或预计配送总时长。

所有明细与所点单次记录一致，展示快照用于追溯，不因最新配送状态变化而把历史步骤或时间当作当前骑手执行建议。


### 2.4 骑手路线规划公共配置

**页面入口与操作**

总后台【公共配置】增加“骑手多单路线规划”配置，样式使用现有文本形式，原型只是展示不需要按照原型效果进行UI设计。按下表展示字段名称进行配置。

| 配置键 | 配置项 | 本次提供值 | 用途与说明 |
| --- | --- | --- | --- |
| open | 总开关 | 1 | 0为全局关闭，1为开启；与平台系统设置的骑手路线规划总开关对应同一配置 |
| speed_kmh | 骑行速度 | 暂定25公里／小时 | 用于由路段距离换算骑行时间，不是骑手实际上报速度 |
| drop_service_minutes | 每单送达交付时长 | 暂定5分钟 | 每笔剩余送达动作的交付停留时间 |
| pickup_service_minutes | 取餐停留时长 | 暂定0分钟 | 每笔剩余取餐动作的停留时间 |
| allow_late_max | 骑手软线容差上限 | 暂定30分钟 | 骑手输入的软线容差不超过该配置；不修改订单真实最晚送达时间 |
| w_late | 超时惩罚权重 | 暂定10 | 仅配置权重；保留软线超时单数优先、总耗时其次 |
| w_remind | 催单提前量权重 | 暂定5 | 仅配置权重；不新增催单排序公式，不改变原两级优先级 |
| carry_limit | 同时取货上限 | 暂定3单 | 达到取货上限后，先规划送货，再规划取货，如果未达到上线，按照时间最短且软超时订单最少进行规划；|
| cache_ttl | 规划结果缓存时间 | 暂定10秒 | 规划结果缓存有效时间；订单或权限变化后失效，不继续使用已失效路线 |
| max_tasks | 参与规划的最大单数 | 暂定10单 | 超过此值时按[3.1.1 规划对象与取送动作](#311-规划对象与取送动作)的支付时间顺序选满；超出的订单列入暂未参与 |
| dist_provider | 距离来源 | tencent | tencent为腾讯骑行，line为直线距离；用于获取路段距离，时间由配置速度换算 |
| matrix_ttl | 距离矩阵缓存时间 | 604800秒（7天） | 距离矩阵缓存有效时间，与规划结果缓存分别配置 |
| include_paotui | 跑腿单是否参与规划 | 0 | 0不参与，1参与；本次默认仍不参与，启用跑腿的业务边界待确认 |
| log_sample | 快照日志采样 | 1 | 1全量，N按1/N采样，0关闭；非负整数，实际日志留存时长另行核对 |

**骑手路线时间读取规则**

1. 每次生成有效规划，读取本次已保存的公共配置；
2. 相邻两站骑行分钟＝该路段距离公里数÷speed_kmh×60；路段距离及异常兜底见[3.1.3 预计到达、预计送达与超时计算](#313-预计到达预计送达与超时计算)。
3. 本步预计到达＝上一步预计完成＋本段骑行时间；第一步从本次位置和规划时间起算。
4. 取餐步骤预计完成＝预计到达＋取餐停留时长（pickup_service_minutes）；送达步骤预计完成＝预计到达＋每单送达交付时长（drop_service_minutes）
5. 最后一单预计完成－本次规划时间为预计总时长；不包含送完后的返程及暂未参与订单的等待。
6. 骑手个人软线容差受allow_late_max限制。路线规划的时候，优先查询该字段最大值，如果骑手设置的超过了该值，按照公共配置设置为准，如果骑手设置的该值不大于公共配置，按照骑手设置为准。
7. 公共速度、取餐停留或交付时长改变并保存后，原当前规划失效，按新参数重新计算整条路线；后台历史记录保留该次规划的原参数和结果，不用新值改写历史时间。
8. open与平台系统设置的路线总开关共用同一保存值，两者均可以控制是否开启骑手路线规划；

**输入与边界**

开关只选0／1；距离来源只选tencent／line。速度须大于0；取餐／交付时长、权重和缓存时间不能为负；容量及最大单数为正整数；软线容差上限与日志采样为非负整数。输入无效时阻止本次保存，并保留原已保存配置；具体管理角色与正式系统失败反馈沿用公共配置页权限后核对。

**与已确认规则的衔接**

时间相关字段本次明确改为读取公共配置，25公里／小时、交付5分钟、取餐0分钟是本次提供的配置值，不能在骑手端另写死。

【修改】路线按carry_limit遵守满载优先送，按max_tasks限制本轮参与单数。w_late／w_remind本次仅配置权重，保留“先软线超时单数、再总耗时”的原优先级，不另造组合公式。跑腿默认0不参与，暂无启用后的功能，本期无跑腿订单功能。


### 2.5 小镇骑手路线规划开关

【新增】总后台进入【小镇管理 → 小镇管理】。点击目标小镇的【编辑】，在【配置信息】的「开启在线联系」下方增加「骑手路线规划」，提供【开启】【关闭】，默认【关闭】。使用本页已有【保存】生效，配置仅作用于该小镇。

平台总开关和骑手所属小镇开关都开启后，新版骑手APP的接单设置在【滑动接单设置】下方显示【骑手多单路线规划】入口，点击进入独立设置页，骑手个人也开启后，外卖接单列表才显示【路线】入口。任一后台开关关闭时，隐藏骑手路线规划设置入口和外卖列表路线入口，权限与已打开页面的处理见[3.1.6 平台及小镇权限、个人开关与容差](#316-平台及小镇权限个人开关与容差)。



## 3. 骑手APP

### 3.1 规则说明

#### 3.1.1 规划对象与取送动作

**功能目的**

将骑手当前待取货和待送货的外卖订单拆成需要完成的“取餐／送餐”动作，再统一安排顺序。不是按接单列表分类分别规划，也不是给每一单各算一条独立路线。

本次订单类型以[1. 功能说明](#1-功能说明)为准，包括已接外卖及闪购订单；只处理仍归本骑手、未完成且可执行的订单。未接新任务不计入在手规划。

**订单状态对应的剩余动作**

| 当前订单情况 | 本次规划如何处理 |
| --- | --- |
| 已出餐、待取货 | 生成“到商家取餐”和“送至收货地”两个动作；本单必须先取后送 |
| 已取货、待送达 | 只生成送餐动作，不再安排回商家取餐 |
| 未出餐、待取货 | 不生成可执行步骤，在“暂未参与”区显示“商家备餐中，暂未参与规划”；出餐后整体重排 |
| 转单中、等待接受 | 不生成可执行步骤，在“暂未参与”区显示“转单中，暂不参与路线规划”；处理结果见[3.1.5 32号订单转单前后如何处理](#315-32号订单转单前后如何处理) |
| 已送达、取消、退款中或已退款、已转出或不再归属 | 从剩余规划移除，不保留已失效步骤 |

**计数与边界**

- “参与订单数”按有可执行动作的独立订单计数；一单待取货虽有两个步骤，也只算一单。
- “暂未参与订单数”统计仍在手的备餐中、转单中、超过本轮规划单数上限的无法安排的订单数；不计入本轮参与数、完整取送步骤或全部完成耗时。
- 同用户、同收货地址订单独立保留状态、时限与确认送达操作。即使路线连续到同一地址，也不合单、不批量确认送达。
- 【修改】本轮参与订单数不超过公共配置max_tasks，本次值10；按独立订单计数，一单取送两步仍占1单。超过上限的订单保留在原接单列表，并在路线“暂未参与”区标明“超过本轮规划单数上限”。订单送达、归属或状态变化及配置保存后整体重排，再按最新上限选入。
- 符合规划条件的订单超过本轮上限时，按订单支付时间从早到晚依次选择，选满max_tasks单。选入后按既有骑手路线规则安排取送。公共规划单数上限仅用于本轮选单，运营商指派和骑手转入沿用原接单规则。


#### 3.1.2 路线顺序如何确定

**先确定可以安排的动作**

以本次规划时的骑手位置和时间为起点，只安排[3.1.1 规划对象与取送动作](#311-规划对象与取送动作)可执行动作。同一订单必须先取后送；已取餐订单只安排送餐。不同订单允许交叉取送，例如“先送18→取32→取45→送32→送45”。

**【修改】携带上限与满载优先送**

- 每次规划读取公共配置carry_limit，本次值3。携带量指已经取货且尚未完成送达或交接的订单数；待取货订单尚未占用携带量。
- 每安排一次取货，后续模拟携带量加1；每安排一次完成送达，减1。达到或超过上限时，先安排已取货订单送达，腾出容量后才可以继续安排取货。
- 例如上限3、当前已携带2单，即使还有4单待取，也只能再取1单；携带3单后下一步须送货，降至2单后才能继续取货。
- 若本次规划开始时已携带超过上限，先送至低于上限再安排取货。转单中的已取货订单在完成实际交接前仍占携带量，不因暂不参加路线而当作已腾空。
- 本限制约束路线建议，不替代原接单上限，不新增取货按钮权限。

**两个优先级，按先后比较**

1. 对一条可行顺序，按[3.1.3 预计到达、预计送达与超时计算](#313-预计到达预计送达与超时计算)逐步累加时间，得到每笔订单的预计完成送达时间。
2. 以“本单真实最晚送达时间＋骑手软线容差”为本次排序比较时限。预计完成送达时间超过该时限，计为一笔“软线超时的订单”；
3. 优先选择软线超时的订单数量更少的候选顺序。
4. 数量相同时，再选择完成全部剩余可执行动作总耗时更短的候选顺序。
5. 两项结果都相同时，本需求不规定唯一顺序；选出的顺序仍须满足先取后送等约束。

w_late、w_remind按公共配置保存。本次仅配置权重，保留上述“软线超时单数优先、总耗时其次”的顺序，不使用加权分数替换，不新增催单优先排序公式。

**比较示例**

以下仅说明优先级，数值为假设的候选计算结果：

| 候选顺序 | 超过排序时限的订单数 | 全部完成耗时 | 比较结果 |
| --- | --- | --- | --- |
| 甲 | 0单 | 35分钟 | 选择甲 |
| 乙 | 1单 | 30分钟 | 虽然更快，但超时单数更多，不优先 |
| 丙 | 0单 | 40分钟 | 与甲超时单数相同，甲更快 |

因此，是否先去A取餐、再去B送餐、然后去C取餐，取决于这条完整顺序中每单能否及时送达及总耗时。不能只比较骑手到A、B、C的距离。


#### 3.1.3 预计到达、预计送达与超时计算

**计算起点与每段骑行时间**

每次重新规划，都以“当前骑手位置＋本次规划时间”重新起算。第一段为骑手当前位置到第一站；后续每段为上一站到下一站，不能把每段都从骑手当前位置重新计算。

| 时间项目 | 计算口径 |
| --- | --- |
| 相邻两站预计骑行时间 | 读取dist_provider对应路段距离，按路段公里数÷公共配置speed_kmh×60换算分钟 |
| 取餐停留时间 | 读取公共配置pickup_service_minutes；本次提供值0分钟，不表示实际取餐没有耗时 |
| 送餐交付时间 | 读取公共配置drop_service_minutes；本次提供值5分钟，包括到达收货点后的交付过程 |
| 地图距离异常 | 获取骑行距离异常时，按两点直线距离（公里）÷本次配置的骑行速度（公里／小时）×60估算分钟 |

【修改】骑行速度统一读取公共配置speed_kmh，本次值25；取餐停留和送达交付时长分别读取对应配置。距离接口及换算结果仍需联调核对。缺位置或时限等无法可靠估算的情况，不编造“准时”结论，见[6.2 实施前需核对](#62-实施前需核对)。

**订单最晚送达时间**

每个取餐和送达步骤读取该订单在订单系统中的「最晚送达时间」。同一订单的取餐、送达步骤显示同一时限。路线重排重新计算预计到达和预计完成送达，订单最晚送达使用订单当前有效记录。骑手软线容差只用于排序比较。

**沿路线逐站累加**

1. 第一步预计到达＝生成本次规划的时间＋第一段骑行时间。
2. 取餐步骤预计离开商家＝本步预计到达商家时间＋本轮配置的取餐停留时长。
3. 送达步骤预计完成送达＝本步预计到达收货地址时间＋本轮配置的每单送达交付时长。
4. 后续步骤预计到达＝上一步预计离开商家或完成送达的时间＋上一站到本站的骑行时间。
5. “全部完成耗时”＝最后一步预计完成时间－本次路线规划的时间，即所有规划路线内的路段骑行＋取餐停留＋送餐交付之和；不含送完后的返程。

**完整计算示例：3单、5个步骤**

假设公共配置speed_kmh=25、pickup_service_minutes=0、drop_service_minutes=5、carry_limit=3、max_tasks=10，12:00开始规划，18号已取货，32号与45号已出餐待取货；本例选定顺序如下，路段分钟为示例给定值。

| 步骤 | 本段骑行 | 本站停留 | 预计到达 | 预计离开／完成 |
| --- | --- | --- | --- | --- |
| 1. 送18号 | 7分钟 | 交付5分钟 | 12:07 | 12:12完成送达 |
| 2. 取32号 | 3分钟 | 取餐0分钟 | 12:15 | 12:15离开 |
| 3. 取45号 | 4分钟 | 取餐0分钟 | 12:19 | 12:19离开 |
| 4. 送32号 | 3分钟 | 交付5分钟 | 12:22 | 12:27完成送达 |
| 5. 送45号 | 0分钟，同收货点 | 交付5分钟 | 12:27 | 12:32完成送达 |

例如18号订单记录的最晚送达为12:13。第一步从12:00开始，骑行7分钟，预计12:07到达；加5分钟交付，预计12:12完成送达。32号预计12:27送达，45号预计12:32送达。总骑行17分钟＋3单交付15分钟＝32分钟，预计12:32全部完成。同收货点只使本例最后一段骑行变为0，两单仍分别交付、分别确认。

**真实超时提示与排序容差分开**

| 用途 | 比较方式 |
| --- | --- |
| 骑手界面“预计超时”及预计超时单数 | 本单预计完成送达时间＞订单真实最晚送达时间。超出几分钟就提示“预计超时N分钟” |
| 路线排序时的超时单数 | 本单预计完成送达时间＞真实最晚送达时间＋软线容差；仅用于比较路线 |

例如：最晚12:30，预计12:27到收货点，交付5分钟后12:32完成，应提示“预计超时2分钟”。若骑手设置允许超时5分钟，该单不计入排序比较的超时数量，但页面仍提示预计超时2分钟。容差不修改真实最晚送达时间，不改变实际超时判定或责任。


#### 3.1.4 何时重新规划及如何替换旧结果

**触发时机**

| 触发事件 | 对全部剩余路线的处理 |
| --- | --- |
| 新接、运营商指派、转入成功 | 纳入最新归属且符合条件的订单，整体重排，不固定插到队尾 |
| 商家出餐 | 将该单取餐、送餐动作纳入，与其他订单一起重新排序 |
| 骑手确认取货 | 去掉本单已完成取餐动作，保留送餐动作，整体重排 |
| 骑手确认送达 | 移除本单剩余动作，重新安排其他订单 |
| 发起转单、转单成功或失败 | 按[3.1.5 32号订单转单前后如何处理](#315-32号订单转单前后如何处理)暂缓、移除或重新纳入，整体重排 |
| 取消、运营商重置、直接退款或其他归属／状态变化 | 以最终有效归属和配送状态重建或移除动作，再整体重排 |
| 进入路线页、点击路线页右上角“刷新” | 重新读取当前在手订单、位置和时间，重算全部路线 |
| 修改并保存个人路线设置 | 按新有效设置更新；个人关闭时清除有效路线和用户旧位次。平台、小镇关闭后的各页面处理见[3.1.6 平台及小镇权限、个人开关与容差](#316-平台及小镇权限个人开关与容差) |

**结果替换规则**

- 每次规划使用最新订单状态、当前位置和当前时间。不是仅移动发生变化的那一笔订单。
- 重新规划开始后，旧地图线路、步骤、下一站、路线预计时间及用户旧位次立即失效；不继续把旧结果作为指引。
- 路线页已打开：先显示“路线更新中”，成功后一次展示整条新路线。停留在订单列表：不强制跳转路线页，进入路线页时读取最新结果。
- 失败显示“路线更新失败，请重试”，不恢复旧路线；重试按当时最新状态重新计算。
- 新一轮状态变化发生后，不得用较早规划结果覆盖较新的取消、退款、转单等有效状态。

具体界面显示及按钮行为见[3.2.3.1 顶部标题栏与进入、返回、刷新](#3231-顶部标题栏与进入返回刷新)的页面状态表。


#### 3.1.5 32号订单转单前后如何处理

**订单列表与路线各自的职责**

路线页只处理本单是否参与当前规划。

**转单状态对应的路线变化**

| 32号订单状态 | 路线页怎么显示 | 其余路线怎么处理 |
| --- | --- | --- |
| 发起转单，等待接受 | 从可执行步骤中暂时移出32号的剩余取／送动作，在“暂未参与”列“#32 张记面馆：转单中，暂不参与路线规划” | 立即按其他可执行订单整体重排；不等转单成功，也不冻结旧顺序 |
| 对方接受，转出成功 | 从原骑手步骤及暂未参与区移除 | 原骑手按当前位置／时间重排；接收骑手按最新归属和配送状态纳入其规划 |
| 对方拒绝或转单失败，仍归原骑手 | 解除转单中提示；已出餐待取货重新加入取餐＋送餐，已取货只加入送餐 | 所有参与订单重新排序，不能直接恢复转单前旧顺序及旧预计时间 |
| 转单期间被取消、退款终止配送或重置 | 按最终有效状态移除或重建 | 不因转单失败把已终止的订单错误加回 |

例如，原路线为“送18→取32→取45→送32→送45”：32号进入转单中后，取32、送32均暂时移出，其他动作重新排序；失败恢复时，以骑手当时位置与时间重算32号及其余订单，结果可能与原路线不同。

转单不延长订单真实最晚送达时间。原转单期间的操作权限、到期结果、已取餐实物交接继续沿用既有业务，不由路线规划另造规则。

**软线容差的含义**

软线容差指骑手为路线排序设置的送达缓冲时间，软线＝订单最晚送达时间＋软线容差。超过订单最晚送达时间计硬超时，超过软线才计软线超时。骑手首次设置时软线容差默认0分钟，已有设置读取最近一次保存值。可输入0～公共配置allow_late_max的整数分钟数，本次上限30分钟。该数值只用于[3.1.2 路线顺序如何确定](#312-路线顺序如何确定)的路线排序比较，不修改订单真实时限；页面真实超时提示仍按[3.1.3 预计到达、预计送达与超时计算](#313-预计到达预计送达与超时计算)计算。平台和小镇开启后，个人开关仍按骑手已保存的设置展示，个人修改点击保存后才生效。

平台或小镇再次开启后的个人设置保留／恢复方式尚未明确，见[6.2 实施前需核对](#62-实施前需核对)；本次不擅自统一重置或打开。

#### 3.2.3.2 当前规划路线数据

**规则说明**

**数据来源与统计时点**

只展示最近一次成功规划的同一份有效结果：订单、取送步骤、预计时间和超时判断必须属于同一轮规划。进入、刷新或订单变化重新规划时，旧统计同步失效；成功后和地图、下一站、步骤一起更新。

**统计口径**

| 显示字段 | 如何统计 |
| --- | --- |
| 当前规划·HH:mm更新 | 本次有效路线的规划时间，不使用页面打开时间冒充更新成功时间 |
| N单参与 | 统计本轮结果中有剩余可执行取／送动作的独立订单；一单有取、送两步仍只计1单。已出餐待取货、已取货待送达按max_tasks选入本轮，并按carry_limit携带约束选入本轮；备餐中、转单中、超过max_tasks的订单等暂不计入；已送达、取消、退款中、已退款、已转出等移除 |
| M分钟完成 | 本轮最后一步预计完成时间－本次规划的时间。等于本次规划路线全部的路段骑行＋取餐停留＋送餐交付的总和；取餐停留与送餐交付分钟分别读取本次公共配置，不含返程，也不含暂未参与订单的等待与交付 |
| K单预计超时 | 对每笔参与订单，用预计完成送达时间与真实最晚送达时间比较；严格超过计1单，等于不计。同一订单只计1次；骑手软线容差仅影响排序，不抵扣页面超时数 |
| 预计HH:mm全部完成 | 取本轮最后一步预计完成时间|
| 暂未参与P单 | 统计当前仍归本骑手、未完成但因备餐中、转单中、超过本轮规划单数上限而未安排动作的独立订单；不计入N、M或K |

**统计示例**

12:00规划：18号已取货，32、45号已出餐，51号备餐中。18、32、45各计1单，显示3单参与、暂未参与1单；5个动作不显示为5单。按[3.1.3 预计到达、预计送达与超时计算](#313-预计到达预计送达与超时计算)的完整例，骑行17分钟＋3单交付15分钟＝32分钟，预计12:32全部完成；3单均未超过各自真实时限时显示0单预计超时。

**UI交互**

位于固定标题栏正下方，使用白色圆角卡片。

| 从上到下 | UI展示与交互 |
| --- | --- |
| 第一行 | 灰字“当前规划·HH:mm更新” |
| 中间指标行 | 从左到右显示橙色大数字及单位：N单参与、M分钟完成、K单预计超时 |
| 底部辅助行 | 灰字“预计HH:mm全部完成·暂未参与P单” |

本卡片用于展示当前规划数据，不新增指标点击筛选或编辑操作。更新中、失败、规划关闭或没有可执行步骤时隐藏旧统计

| 订单情况 | 显示内容及更新结果 |
| --- | --- |
| 商家未出餐 | “商家备餐中，暂未参与规划”；出餐后整体重排，纳入取餐＋送餐动作 |
| 转单中等待接受 | “转单中，暂不参与路线规划”；成功后移出原骑手规划，失败仍归本骑手时按最新状态重新纳入 |
| 超过本轮规划单数上限 | “超过本轮规划单数上限”；仍保留在原接单列表，下一轮按最新订单的支付时间和上限重新选单 |
| 携带容量暂未释放 | “携带容量暂未释放，等待已取货订单送达或交接”；已取货转单暂缓订单仍占容量时，不安排超上限取货 |

没有可执行步骤但还有暂未参与订单时，先显示“暂无可执行取送步骤”，下方继续逐笔列出原因。订单已送达、取消或退款终止配送时移除，不留在本区。


#### 3.2.3.7 底部说明与订单操作边界

**规则说明**

路线顺序和时间作为配送建议；接单、联系、转单、取消、取货及确认送达继续通过原接单列表执行。本页不新增上述订单操作，也不新增单站导航。

**UI交互**

位于页面最下方，以灰色小字显示“顺序与时间为建议，订单操作请返回接单列表”。没有可执行结果、更新中或失败时也保留说明。需要操作订单时使用顶部【返回】回到进入前列表分类。



## 4. 用户端

### 4.1 用户前方单数口径

【修改】用户在本人订单详情的地图中查看排队信息。待骑手取货且商家已出餐，本单有有效规划时，骑手地图气泡展示前方单数和距离。骑手已到店时也使用这一气泡内容。取货进入配送中后，距离目标切换为用户收货位置。

**显示位置与状态**

| 本单情况 | 骑手图标上方展示 |
| --- | --- |
| 待取货、商家已出餐且本单纳入有效规划 | 第一行显示“你的前面还有N单”，第二行显示“距离商家 Xm”。无论骑手是否已到店，均优先使用这两行，零单按下表提示展示 |
| 已取货、配送中 | 第一行仍按本单有效规划显示前方单数；第二行改为“距离用户 Xm” |
| 有效规划中，前面没有其他送达订单 | 第一行沿用“骑手正为你配送”；第二行仍按尚未取货／配送中分别显示距商家／用户的米数 |
| 待取货、商家未出餐 | 沿用现有待取货地图逻辑。未到店显示距商家；已到店显示“骑手已到店”和“商家备餐中，骑手取货后将尽快配送” |
| 转单中 | 暂不展示路线排队数量，保持现有逻辑样式 |
| 规划关闭、重排中、失败或本单未纳入有效规划 | 清除路线位次，沿用现有订单地图。待取货时按商家出餐、骑手到店状态恢复原气泡 |
| 已送达、取消、退款终止配送或配送归属变化 | 按当前订单状态展示，清除原骑手旧位次及不适用的距离信息 |

**前方单数与距离口径**

- 前方单数只统计本单送达动作之前其他订单的送达动作，取餐不占位。同用户／同地址订单仍分别计数，不把剩余步骤数或骑手全部在手单数当作前方单数。
- 尚未取货时，骑手气泡显示的距离是骑手距离本单商家；已取货配送中时，改为当前骑手位置至本单用户收货位置。均显示米数，沿用订单地图已有距离数据来源和格式，跟现有逻辑一样。
- 骑手定位和地图距离数据更新时更新米数；本单取货状态变化时切换距离目标；路线重排成功时更新位次。
- 用户端沿用现有预计送达逻辑，展示用户成功支付时记录在订单上的送达区间。路线重排只更新前方单数，订单状态卡下方文案继续按原配送状态显示。
- 订单变更使旧位次同步失效；更换骑手后按新骑手的有效规划与位置更新，不继承原位次。


### 4.2 用户订单详情展示

**页面布局与信息分工**

沿用现有订单详情页面，在地图骑手图标上方增加前方单数，并在下一行显示距商家或用户的米数；下方状态卡保留预计送达，不展示骑手完整路线。

| 从上到下的区域 | 展示与操作 |
| --- | --- |
| 【原有／复用】标题栏 | 橙色顶栏，中间“订单详情”，左侧返回，右侧保留原小程序胶囊样式 |
| 【修改】地图与骑手气泡 | 位于标题栏下，按本单状态及是否纳入有效规划，依[4.1 用户前方单数口径](#41-用户前方单数口径)显示骑手气泡 |
| 【原有／复用】订单状态卡 | 白色卡片展示本人当前状态及原进度条；更多、催一下、联系商家、投诉建议及配送时间修改提示沿用原功能及权限 |
| 【原有／复用】预计送达 | 按[4.1 用户前方单数口径](#41-用户前方单数口径)读取订单记录的送达区间。状态卡顶部显示日期和起止时间，例如“预计 12月15日 15:28–15:48 送达”。订单状态放在时间下方，接原进度条和操作按钮 |
| 【原有／复用】门店、商品与费用 | 保留原门店、商品、数量、费用、优惠及本人订单信息，不因路线规划调整商品价格、收费或优惠规则 |

**排队展示与更新**

地图骑手图标上方的橙色圆角气泡按[4.1 用户前方单数口径](#41-用户前方单数口径)显示“你的前面还有N单”或“骑手正为你配送”，下一行显示距离，气泡随骑手标记位置展示。地图下方的状态卡只展示一次预计送达时间，前方单数保留在地图气泡。预计送达区间和下方状态文案沿用现有逻辑。待取货时，下方按商家出餐与骑手到店状态组合展示，例如“商家已出餐，骑手已到店”。

订单或路线状态变化后按[4.1 用户前方单数口径](#41-用户前方单数口径)更新，进入详情和刷新也读取最新有效规划。重排中或失败时隐藏旧位次，按当前配送状态显示现有气泡和状态文案。备餐中、转单中及已完成等分别展示本人当前订单状态。距离沿用订单地图数据与格式，随本单取货状态切换到商家／用户目标，不把缺失数据显示为0m。

用户只能看本人订单信息，不提供其他订单列表或明细。



## 5. 测试重点

1. 混合待取货／待送达时先取后送、可交叉；未出餐和转单中不进入执行序列。
2. 两级排序、读取公共配置的骑行／取餐／交付时长及超时临界值正确；容差影响排序，不掩盖真实超时。
3. 新接、取送、转单、拒绝失败、运营商重置／退款均整体重排，旧路线、旧位次立即失效，失败不恢复旧结果。
4. 列表沿用原转单中样式，不新增五分钟锁定提示或按钮禁用；路线单列转单中提示、暂不排取送。成功更新双方路线，失败后按最新状态重新纳入；退款或重置后不错误加回。
5. 接单上限只限制主动抢单，指派／转入可继续参与；同用户／同地址订单不漏单、不合并确认。
6. 用户前方数量仅数其他送达动作，取餐不占位；核对待取货时未出餐沿用现有气泡，已出餐且纳入有效规划时优先显示前方单数和距离，即使骑手已到店。重排、关闭、失败或未入选时恢复原气泡，预计送达区间和下方状态文案按原逻辑显示。
7. 原列表操作、路线刷新／返回、平台、小镇、个人开关及新旧APP组合按[6. 新旧版本兼容与待核对项](#6-新旧版本兼容与待核对项)回归。
8. 核对原三业务／四状态菜单、列表状态数量、头像→个人中心→右上角设置→设置界面→接单设置（右侧“新增多单路线规划功能”）→滑动接单设置下方的骑手多单路线规划→独立设置页→返回；平台和所属小镇均开时显示文案与入口，任一方关闭时两者均隐藏；路线入口不遮挡状态分类和原有操作，旧版不出现路线入口或新增规划设置。
9. 订单卡片的取送标识、时间、地址、距离与原UI对应；长地址／配送偏好可换行，操作按钮可见可点。新任务尚未接单不进入在手路线，列表与路线的订单范围不混淆。
10. 检查小镇字段位于「开启在线联系」下方，默认关闭，保存才生效。仅平台和所属小镇均开时显示骑手设置，个人也开启后外卖列表才出现路线入口。小镇保存关闭后，旧路线和用户旧位次失效。
11. 分别在设置页、路线页、列表停留时关闭平台。在独立设置页保存时提示并刷新隐藏规划设置内容，返回接单设置后隐藏新增入口；刷新路线或因订单变化重规划时显示“总部关闭了路线规划权限，暂不可查看”；刷新列表后隐藏路线入口。小镇关闭及跨小镇隔离按[3.1.6 平台及小镇权限、个人开关与容差](#316-平台及小镇权限个人开关与容差)核对。
12. 平台和所属小镇开启、个人关闭时，设置仍可编辑。个人开启并保存后恢复列表路线入口。
13. 出餐状态变化后整体重排；重复出餐不重复取餐，取消／退款／转出后的出餐信息不加回已终止订单。
14. 用[3.1.3 预计到达、预计送达与超时计算](#313-预计到达预计送达与超时计算)示例核对：五步预计时间依次12:07／12:15／12:19／12:22／12:27到达，三单完成12:12／12:27／12:32，总耗时32分钟；本例公共交付时长5分钟，同地址仍各自计入交付。
15. 超时边界：预计完成等于最晚时间不超时；预计12:32完成、最晚12:30时提示2分钟，即使容差5分钟也不能隐藏真实超时。
16. 地图点按“#订单短号 取／送”展示（如#18取、#18送），步骤行仍按取送顺序列出；点击后只切查看信息，不改顺序／订单；返回第一站可恢复第1步，刷新后回到新第1步。列表顶部路线工具区显示“建议下一站:动作 · #短号 地点”，取餐显示商家、送餐显示地址，名称过长可换行，重排后同步更新。
17. 路线标题栏滚动时保留；更新中、失败、无在手、全部暂缓、个人关闭、平台关闭及小镇关闭等状态按[3.2.3 路线页面](#323-路线页面)逐项核对。



## 6. 新旧版本兼容与待核对项

### 6.1 新旧版本行为

| 组合或状态 | 兼容规则 |
| --- | --- |
| 旧骑手APP | 保留原接单、取货、送达、转单、联系等流程，不要求旧版出现路线入口 |
| 新骑手APP，平台或小镇关闭 | 新进入时隐藏路线入口和规划设置。已打开页面按[3.1.6 平台及小镇权限、个人开关与容差](#316-平台及小镇权限个人开关与容差)的触发时机处理 |
| 新骑手APP，平台和小镇开启、个人关闭 | 隐藏列表路线工具及入口，保留可编辑的规划设置；个人开启并保存后才显示入口，不展示无效路线 |
| 新骑手APP，平台、小镇和个人均开启 | 新增独立路线页；订单更新触发新路线，不改变已有订单状态含义与操作权限 |
| 旧用户APP | 继续原订单详情和配送展示，不强制新增排队文案 |
| 新用户APP＋有效规划 | 展示本人前方单数，沿用订单记录的预计送达区间 |
| 新用户APP＋旧骑手APP或无有效规划 | 无有效规划时仅沿用原订单展示，包括订单记录的预计送达区间；有有效规划时按新版规则展示前方单数 |

不以本需求新增强制升级或改变原派单规则。新信息缺失时不能显示默认0单，也不能把无结果误报为“骑手正为你配送”。

各端仅按实际支持范围展示新功能，不因总部开关强制旧版出现新入口。


### 6.2 实施前需核对

- 具体APP支持版本及骑手个人开关的首次默认状态。
- 转单5分钟到期的实际结果、已取餐转单交接条件；退款处理中配送权限，沿用现有业务后再核对。
- 联调核对订单系统「最晚送达时间」的字段及其生成口径。缺位置或时限数据时，核对无法可靠估算的处理及提示。
- 公共配置读取、按速度换算骑行时间及真实地图、订单事件联动需联调，原型演示不代替实机验收。
- 平台或小镇再次开启后，骑手此前个人开关及软线容差的保留／恢复策略；当前未明确，不自动清空或统一开启。
- 总后台配置的具体管理角色与保存失败反馈沿用现有设置页后核对；已打开APP接收平台及小镇权限变化的实际同步需联调验证。
